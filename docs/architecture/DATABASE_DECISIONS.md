## ADR 001: Physical Separation of Central and Operational Databases

### Context
In enterprise human resource management across distributed branch networks, branch locations require uninterrupted operational uptime for daily attendance check-in/out, roster dispatching, and leave requests, even during central network interruptions, scheduled maintenance, or corporate query spikes.

### Decision
Deploy **two physically independent Supabase PostgreSQL 17 projects**:
1. `nexus-central` (`wcmevigbqsmzsdqidjel`)
2. `nexus-branch-a` (`uneycmbqqpkifwhwzbes`)

### Consequences
- **Positive:**
  - True partition tolerance. Network outages or maintenance on Central do not disrupt Branch A attendance.
  - Sub-10ms query latency for branch operations since data is processed against the local database.
  - Clean horizontal partitioning model ready for future branches (`nexus-branch-b`, etc.).
- **Trade-offs:**
  - Relational joins across nodes cannot be performed at the database engine level.
  - Cross-node data consistency is eventually consistent, managed via asynchronous replication.

## ADR 002: Global UUID Identity Strategy & Logical Cross-Node References

### Context
When records are authored on autonomous operational nodes and synchronized to Central, integer sequences (`BIGSERIAL`) cause primary key collisions across branches. Additionally, PostgreSQL engine constraints cannot cross physical database instances.

### Decision
1. All tables across both nodes use **UUIDv4 (`gen_random_uuid()`)** as their primary key.
2. Cross-node associations (e.g. `nexus-branch-a.employees.user_auth_id` pointing to `nexus-central.auth.users.id`) are modeled as **logical references** without PostgreSQL DDL `REFERENCES` clauses.
3. Central projection tables retain the exact UUID generated by the branch master.

### Consequences
- **Positive:**
  - Globally unique, collision-free identity across all nodes without centralized coordinate locking.
  - Branch A records can be generated while offline and inserted directly into Central without re-keying.
- **Trade-offs:**
  - Referential integrity across nodes must be validated by the sync worker and application logic.

## ADR 003: Transactional Outbox / Inbox Pattern with Optimistic Leases

### Context
Supabase provides built-in Realtime replication over WebSockets. We must establish a durable replication engine for cross-project data synchronization.

### Decision
**Reject Supabase Realtime for database-to-database replication.** Adopt the **Transactional Outbox & Idempotent Inbox Pattern** executed by a dedicated server-side synchronization worker.

### Justification
- Supabase Realtime is a client-facing WebSocket push mechanism designed for single-database UI updates. It provides no guaranteed delivery, durable replay buffers, dead-letter routing, or cross-project transactional atomicity.
- The Transactional Outbox guarantees **Atomicity**: the domain mutation and outbox record commit in the exact same local PostgreSQL transaction on Branch A.
- To safely support concurrent sync workers, `sync_outbox` uses **optimistic lease claiming** with `FOR UPDATE SKIP LOCKED`, storing `locked_by` and `locked_at`.
- Expired claims (`locked_at < now() - INTERVAL '5 minutes'`) are safely reclaimed if a worker crashes.
- The Central Inbox guarantees **Idempotency** via `event_id UUID UNIQUE NOT NULL` and `ON CONFLICT (event_id) DO NOTHING`.
- **Delivery Guarantee:** At-least-once delivery with idempotent processing (Effectively-Once semantics).

## ADR 004: Central Employee Directory as a Read-Only Projection

### Context
Corporate HR and executive management need to search and view employee records across all branches without executing distributed fan-out queries across every individual branch database.

### Decision
Model `nexus-central.employee_directory` as a **read-optimized projection** populated exclusively via asynchronous sync events (`EMPLOYEE_UPSERTED`, `EMPLOYEE_DEACTIVATED`).

### Rules
1. Branch A is the sole operational master of its employee records.
2. Web clients cannot execute `INSERT`, `UPDATE`, or `DELETE` directly on `employee_directory`.
3. Central DDL strictly enforces `version BIGINT` optimistic concurrency checks: updates are applied only if `incoming.version > current.version`, discarding out-of-order stale events.

## ADR 005: Centralized Attendance Daily Summaries for Corporate Reporting

### Context
Replicating all raw operational attendance logs (check-in/out timestamps, IP addresses, photos, sensor telemetry) to Central creates massive unnecessary data volume and synchronization complexity. Central management only requires aggregated daily compliance and attendance metrics.

### Decision
Introduce `nexus-central.attendance_daily_summaries` to store aggregated daily attendance rollups from Branch A.

### Rules
1. Grain: `UNIQUE (branch_id, summary_date)`.
2. Metrics: `total_employees`, `present_count`, `late_count`, `absent_count`, `leave_count`.
3. Invariant: `CHECK (present_count + late_count + absent_count + leave_count <= total_employees)`.
4. Recalculation: If a branch manager retroactively corrects an attendance record, Branch A recomputes the rollup for that date, increments `source_version`, and dispatches an update. Central applies updates only if `incoming.source_version > existing.source_version`.
5. Consistency: Eventually consistent (not real-time).

## ADR 006: Unidirectional Synchronization Policy for Phase 1

### Context
Bidirectional multi-master synchronization introduces distributed race conditions, write cycles, and split-brain resolution requirements that introduce significant risk in initial system deployments.

### Decision
Phase 1 implements **strictly Unidirectional Synchronization (Branch A $\rightarrow$ Central)**.

### Rules
1. Operational data flows exclusively from Branch A to Central.
2. Corporate branch configuration (`branches`) is mastered in Central. Branch A receives its branch identity during deployment/provisioning via its local `branch_config` singleton table.
3. No continuous Central $\rightarrow$ Branch A replication pipeline is active in Phase 1.

## ADR 007: Composite Foreign Keys for Intra-Node Relational Integrity

### Context
In distributed databases, data integrity bugs that allow invalid associations (e.g. assigning an employee to a position in a different department, or logging attendance against another employee's schedule) create severe synchronization and domain corruption.

### Decision
Enforce database-level relational integrity via **composite foreign keys**:
1. Table `positions` includes `UNIQUE (id, department_id)`.
   Table `employees` enforces:
   `FOREIGN KEY (position_id, department_id) REFERENCES positions(id, department_id) ON DELETE RESTRICT`.
2. Table `employee_schedules` includes `UNIQUE (id, employee_id)`.
   Table `attendance` enforces:
   `FOREIGN KEY (schedule_id, employee_id) REFERENCES employee_schedules(id, employee_id) ON DELETE RESTRICT`.

### Consequences
- Invalid assignments are rejected at the PostgreSQL engine level, preventing reliance on frontend validation alone.

## ADR 008: Strictly One Shift Per Employee Per Day (Phase 1 Decision)

### Context
Allowing multiple shifts per employee per day significantly complicates roster conflict resolution, split-shift attendance calculations, and daily summary rollups.

### Decision
In Phase 1, an employee may have **strictly ONE assigned shift per calendar day**.

### Implementation
Enforced in `employee_schedules` via:
```sql
UNIQUE (employee_id, schedule_date) WHERE (status != 'CANCELLED')
```
Cancelled schedules do not block re-rostering, but multiple simultaneous active shifts are strictly prohibited.

## ADR 009: Deterministic Branch Config Singleton Enforcement

### Context
A naive `CHECK (id IS NOT NULL)` condition does not prevent multiple rows from being inserted into a configuration table.

### Decision
Enforce a single-row guarantee on `nexus-branch-a.branch_config` using a constant UUID primary key:
```sql
id UUID PRIMARY KEY DEFAULT '00000000-0000-0000-0000-000000000001'::uuid
  CHECK (id = '00000000-0000-0000-0000-000000000001'::uuid)
```

### Consequences
- Any attempt to insert a second configuration record produces a primary key collision at the database engine level, physically guaranteeing a singleton table.

## ADR 010: Concurrency-Safe Sequential Employee Code Generation

### Context
Generating employee badge codes using `COUNT(*) + 1` causes catastrophic race conditions, duplicate key violations, and re-used codes when soft deletions occur.

### Decision
Employee codes for Branch A follow the format `EMP-A-0001` (and `EMP-B-0001` for future branches), generated via a dedicated PostgreSQL sequence:
```sql
CREATE SEQUENCE seq_branch_a_employee_code START WITH 1 INCREMENT BY 1;
```
A `BEFORE INSERT` trigger function populates `NEW.employee_code := 'EMP-A-' || lpad(nextval('seq_branch_a_employee_code')::text, 4, '0')`.

## ADR 011: Canonical Timestamp, Display Timezone, and Chronology Validation

### Context
Inconsistent timezone handling causes attendance check-in disputes, calculation discrepancies, and shift boundary errors. Additionally, dynamic `now()` expressions inside table `CHECK` constraints violate PostgreSQL immutability requirements.

### Decision
1. All timestamp columns across both nodes use **`TIMESTAMPTZ`** (internally stored in UTC).
2. The standard display timezone is **`Asia/Jakarta` (WIB, UTC+7)**.
3. Overnight shifts are supported via:
   ```sql
   CHECK ((is_overnight = FALSE AND end_time > start_time) OR (is_overnight = TRUE AND end_time <= start_time))
   ```
4. Attendance check-out chronology is enforced via:
   ```sql
   CHECK (check_out_time IS NULL OR (check_out_time > check_in_time AND check_out_time <= check_in_time + INTERVAL '24 hours'))
   ```
5. Check-in future-time validation is enforced via backend API business logic and a `BEFORE INSERT` trigger, preserving constraint determinism.

## ADR 012: Soft Deletion Strategy with Permanent Identity Preservation

### Context
Hard `DELETE` operations on employee records destroy historical attendance logs, invalidate audit trails, and break compliance records.

### Decision
1. Operational employee records implement soft-deletion via `is_deleted BOOLEAN NOT NULL DEFAULT FALSE` and `deleted_at TIMESTAMPTZ`.
2. Hard `DELETE` operations are revoked from application roles and blocked by a defensive `BEFORE DELETE` trigger.
3. `employee_code` and `email` maintain permanent global uniqueness (`UNIQUE (employee_code)` and `UNIQUE (email)` across all rows, including soft-deleted) to prevent badge recycling and historical identity confusion.

## ADR 013: Backend Authentication Gateway with Cryptographic JWT Verification

### Context
`nexus-central` and `nexus-branch-a` are independent Supabase projects with distinct internal secrets. Branch A does not automatically trust Central tokens or share signing keys.

### Decision
1. Direct browser connections to Branch A are prohibited.
2. All branch requests route through a Backend Application Gateway.
3. The Gateway receives Central-issued JWTs, verifies the cryptographic signature against Central Auth's public JWKS endpoint (`/.well-known/jwks.json`), and validates token claims (`exp`, `user_role`, `branch_id`).
4. Only upon successful cryptographic verification does the backend interact with Branch A using server-side credentials, enforcing authorization context.
